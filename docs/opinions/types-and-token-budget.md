# 把token预算花在可用答案上

v4给我最直接的启发是：提示更短并不总意味着更高效。多写一句类型要求，在这批Kimi配对中让总token从9,820增加到10,796，却让正确答案从9个增加到25个。每个正确答案对应的token由1,091.11降到431.84。这是[本轮数据](../studies/token-efficiency-v4-findings.md)支持的观察，不是所有模型通用的优化公式。

这里的“可用”需要具体定义。本项目要求程序能读出符合题目类型的answer，并通过预先固定的参考检查。数字字符串可能让人看懂，却不符合接口约定；真正的number也可能算错。因此格式、类型、内容三项应该分别记录。只说“JSON输出率100%”会掩盖内容错误，只看最终正确率又不容易知道该修哪里。

这也解释了为什么不能把结果写成“节省60.4% token”。60.4%是Kimi这批有效配对的每个正确答案用量下降；单次请求的平均总用量反而上升。失败用量未知，输入和输出计价不同，真正账单还需要更多信息。没有跑过修复调用，就不能说省下了多少次修复。

DeepSeek提供了必要的反例：配对正确26→28，总token增加16.7%，每个正确答案的token反而上升8.4%。四次改善与两次退步同时发生，其中有原本正确的计算被改错。类型已经比较可靠时，同一句提醒的边际收益可能很小。当前样本也不足以证明提醒会导致算术退步。

我倾向于把这些发现用于建立测量顺序：先固定任务的验收条件，再拆开格式、类型和内容错误，最后在同一批任务上比较用量。若加入转型、Schema或自动修复，应把规则、拒绝情况、额外请求、延迟和用量一起登记。这些是由实验引出的工程判断，后续仍要用真实任务验证。

本轮只有16道已知家族的新实例、每题两次。它说明值得测试哪一种改进，不足以指定全局最佳提示。项目保留2次网络失败、所有原始输出与退步案例，正是为了让结论可以被重新检查，而不是把偶然高分包装成普遍规律。
