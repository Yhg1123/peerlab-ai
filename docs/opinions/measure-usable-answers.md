# 从省token到可用答案，需要多把尺子

2026-10-02 · 基于[24题、288次请求的复测](../studies/token-efficiency-v2-findings.md)

**这轮让我更重视“应用收到的结果能否直接使用”。** 把一个实验压缩成正确率或节省百分比，很容易漏掉另一侧的变化。我们新增先依据后答案后，DeepSeek答对40/48，明显高于仅答案17/48；但满足全部输出约束且答对的只有27/48。Kimi对应数字则是22/48和10/48。

这些分数并不矛盾：它们在回答不同的问题。答案正确率检查answer是否匹配参考；完整契约还要求短依据、字段和顺序。若一个应用真的需要短依据用于列表展示或结构化存储，超长就是交付问题。若另一个应用允许长解释，就应在自己的实验开始前采用不同契约。不能看完结果后换门槛，让分数更好看。

## 解释可能有帮助，但帮助需要付出预算

对这批任务，DeepSeek的先依据后答案相对仅答案多用69.5%的总token，却多答对23次；分摊到每个正确答案上的token从303.5降至218.6。这是一个值得复验的方向：单次请求更长，也可能因为正确产出更多而更有效率。

Kimi则多用73.9%的token，多答对5次，分摊token从385.1升至517.5。同一条提示策略在两个配置上得到不同的取舍，足以提醒我们分别测量。这里没有按供应商价格换算费用，也没有给用户任务价值设统一权重，所以不据此宣布某个模型更划算。

新策略同时改了字段顺序、依据内容、长度要求和一致性提醒。我们观察到了整套策略的差异，但不知道各因素的贡献。把结果称为“先写理由就会提升能力”会超出证据；下一步需要拆开因素。

## 更多重复，让问题从总分里浮现

DeepSeek新条件有17/24道题两次都答对，还有6题一次对、一次错。Kimi新条件9/24道题两次都对。只取第一次或最好一次会得到另一幅图景，也会隐去这种变化。

“回答一致”又是另一个维度。两次都把字符串当数组，答案可以完全相同，却始终无法被接口按题目类型消费。反过来，两个小数写法不同，也可能都在容差范围内。因此稳定性、语义正确和结构约束应分别记录。

## 一个具体的退步比一句总评更有用

Kimi的数组题在仅答案条件下两次正确；先依据后答案时，它两次都给出了装着数组文本的字符串。人读起来差不多，严格程序接口却不能直接使用。另一个概率题里，依据写出了正确的1/3，answer却压缩成0.3333，丢失了任务要求的精度。

这些例子让改进方向更具体：可以另行测试更明确的类型约束、精度要求和输出验证。它们仍是候选方案，本轮没有验证加入这些措施后会如何改变用量、正确率或延迟。不能因为能解释一个失败，就当作已经修复它。

## 我会如何使用这批结果

我会先确定一个实际任务需要的质量和格式门槛，再分别比较候选策略的完整用量、有效产出、延迟和失败。如果要重复运行，就同时看始终正确的题目比例；如果关心数值，则保留原来的精度要求，并用额外阈值诊断错误来源。

本轮为这些选择提供了可检查的记录：计划先于调用、48个配对来自24道题、所有288条响应公开、参考和分数能离线复核。结果既给出了新策略的收益，也暴露了长度、类型和精度问题。下一步的实验应该针对这些具体问题提出假设，而不是继续追求单独一个好看的百分比。
