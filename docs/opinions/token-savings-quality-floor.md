# 省 token，先给质量设一道门槛

2026-10-02 · PeerLab 实验笔记 · 基于[Token 效率实验 v1](../studies/token-efficiency-v1-findings.md)

**我的观点：省token的优化，应当先满足任务的最低质量要求，再比较用量。** 如果起点正确率很低，保住同样的正确率不足以证明方案值得部署。解释的价值也需要单独评价，不能因为答案字段得分相同，就认定它可有可无。

我们做了96次请求的2×2实验，把系统提示词长短、是否要求解释分开控制。在同题有效配对里，两个因素一起压缩，DeepSeek总token少了53.9%，Kimi少了72.3%。与此同时，DeepSeek只有3/11对答对，Kimi只有3/12对答对。两边都保留了原来的对错模式，也保留了原来的低正确率。

这个结果里，用量下降是真实返回数据支持的事实；“质量已合格”没有证据支持。小题集里没观察到退步，也没有证明在更大任务分布上不会退步。更合适的实践流程，是先约定最低准确率、结构化输出成功率和可接受缺失比例，再看节省是否有业务价值。本轮没有预设这些业务门槛，所以只发表描述性观察。

## 给应用真正需要的输出留预算

本轮省下的大头来自输出。保持常规提示词，仅去掉解释，DeepSeek总token减少45.0%，Kimi减少68.2%。这让我更愿意首先检查应用是否真的消费每个输出字段，再决定哪些字段可以缩短。

但本实验只对answer判分，没有评价解释能否帮助人类审查。关键路径题里，DeepSeek把answer写成12，解释却推到10；解释暴露了矛盾，删掉它也删掉了这条诊断线索。对于必须解释依据的任务，解释就是产品的一部分，应当单独设质量指标。这类场景不适合直接照搬answer-only。

## 输入更短，总量仍可能更高

DeepSeek保留解释时，短提示词让输入减少240token，却让输出多了398token，总量增加5.6%。其中一道任务生成了700token输出并被截断。这次反例让我倾向于用完整请求的用量做优化目标，并一起观察失败与截断。

不能由这个单次反例推导“短提示词会让模型啰嗦”的普遍规律。我们改动了措辞，模型采样也有随机性。它能否稳定出现，需要另外增加重复次数。

## 格式、正确性和账单是三件要分别量的事

一条仅答案响应因为多一个引号而失败；另一条长响应在最后写出了正确答案，但返回了多个JSON块，程序无法按预定契约消费。对自动化工作流而言，我更看重“按约定格式返回、答案正确”的联合结果。遇到失败时应该记录，而不是事后随意改解析规则挑出一个正确数字。

token也没有统一的单价。输入、输出和缓存计费不同，缓存命中仍属于输入用量；供应商usage中有这些分类字段。我们保存了原始usage，但没有测账单，因此只谈token变化。未知缓存或失败请求用量也不能直接补成零。[DeepSeek字段说明](https://api-docs.deepseek.com/api/create-chat-completion/)、[Kimi字段说明](https://platform.kimi.com/docs/api/chat)。

## 下一步值得检验的想法

我想进一步检验“先简答、验证失败再定向修订”：简单任务走短输出，发现明确错误后才增加调用。要验证它，需要把验证器、修订调用、失败请求的用量都计入，并与固定预算的对照组比较；还要防止验证器漏掉错误。本轮没有做这个实验，不能提前宣称它更省。

目前能提出的判断是：先定义什么算可用结果，保留失败与原始数据，用同题配对计算完整用量，再决定输出格式和提示词长度。PeerLab这批数据既记录了节省，也留下了正确率仍低的证据。
