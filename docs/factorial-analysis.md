# 怎样阅读字段顺序与依据限长实验

v3的问题来自v2：简短依据似乎帮助了部分数值题，但它同时改变了字段顺序、内容要求、长度要求和一致性提醒。因此，v2的好成绩不能独自证明“把答案写在最后就会更准确”。v3保留同样的两字段内容要求，只交叉改变请求顺序和是否限长。

## 看四条配对比较，别只找最高分

|比较|保持一致|改变什么|
|---|---|---|
|order_bounded|依据≤80字符|先答案→先依据|
|order_unbounded|依据无明确字符上限|先答案→先依据|
|remove_cap_answer_first|先答案|删掉80字符上限句|
|remove_cap_evidence_first|先依据|删掉80字符上限句|

这是提示词干预：模型收到不同的要求，但未必按要求输出。主分析按请求条件归组，不把不遵守顺序的响应事后挪到另一组。每个比较的质量和用量来自同模型、同题、同重复的有效配对；不能把不同覆盖率的全组总量直接相除。

每个比较都看三个数：正确数如何变化，实际报告的总token如何变化，改善了多少次又退步了多少次。净分数相同也可能隐藏互相抵消的错误。节省率为负表示增加用量，不表示程序出错。token不是人民币账单，缓存折扣和不同模型定价不能忽略。

## 为什么有两种“合格且正确”

假设两个答案都正确，都有顺序正确的answer和evidence，但依据是100个字符。限长组违反自己的要求，不限长组则没有违反长度要求。若只看“本条件契约合格且正确”，删除约束就会让指标上升，即使答案完全没变。

因此另报“共同契约且正确”：四组都检查仅两个字段、非空字符串依据和该组要求的顺序，均不检查长度，再与原有答案判分相交。独立的“≤80字符”计数则对所有组用同一尺子测量。表中的契约类型指依据字符串等结构要求；最终answer的严格类型由答案判分器负责。契约合格不证明依据真实，数值碰巧正确也不证明解释正确。

## 交互项在回答什么

交互项 = 不限长时的顺序效应 − 限长时的顺序效应。例如限长时先依据多对10个百分点，不限长时多对30个百分点，交互项就是+20个百分点。它描述两个因素是否表现出不同的组合效果，不是额外一组模型成绩。

这一计算要求同模型、同题、同重复四个条件都返回。缺一组就不进入交互计算，但已返回的记录仍可进入条件统计或其他有效两组比较。交互项的token单位是每完整区组的token差中之差，不能和节省百分比混用。

## 重复、分层和区间

每题每组采样两次，用于观察同一道题是否稳定。32次返回来自16道题，不能写成32道独立题；其中12道生成题仍只覆盖Bayes和macro-F1两个家族。按题ID聚类的bootstrap保留同题重复，仍没有消除同一家族参数题之间的相关性。

因此所有95%区间都是这个人工选择集合的描述，不是总体保证，也没有多重比较校正。区间跨0不能证明两个提示等价；区间不跨0也不等于可直接推广到业务。类别分数、容差敏感性、格式诊断和反例帮助定位原因，不能代替独立留出集验证。

## 自己复核

```bash
# 无网络、无密钥：核对计划、提示、记录顺序并重算每条答案
python -m peerlab analyze-efficiency examples/token-efficiency-v3/run.json --output runs/v3-recheck
# 可选安装matplotlib后生成可发表的PNG和SVG；核心工具仍无依赖
python scripts/plot_efficiency.py examples/token-efficiency-v3/run.json --output runs/v3-figures
```

`analysis.json`给出基础配对及记录ID，`dimensions.json`给出分层与区间，`factorial.json`给出契约组成和交互。`run.json`保留实际提示、响应、模型名、终止原因、延迟和完整usage；`provenance.json`记录原始文件SHA256和执行commit。SHA256用于发现字节变化，不是供应商对响应真实性的签名。
